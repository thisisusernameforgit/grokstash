# Grokstash

Песочница для отладки Logstash-пайплайнов. Правите `.conf` в браузере, Logstash подхватывает его за секунду, вставляете лог и видите, какие поля получились. Elasticsearch и Kibana не нужны.

Проект сделан под **ARM macOS**: Apple Silicon (M1-M4), Docker Desktop, локальный запуск. Все образы multi-arch, `platform:` в compose не задан, эмуляция не нужна. Linux и x86_64 работать должны, но это не проверенный сценарий.

## Схема

```
Браузер  =>  nginx:80  =>  backend:4000  =>  logstash:1514
         <=  backend:4000/api/event  (обратный канал)
```

| Контейнер | Образ | Порты |
|---|---|---|
| `grokstash_frontend` | nginx, фронтенд собирается в Node | 127.0.0.1:80 |
| `grokstash_backend` | python:3.12-slim | 4000 - только внутри сети |
| `grokstash_logstash` | docker.elastic.co/logstash/logstash | 1514/tcp+udp, 127.0.0.1:9600 |

Backend отправляет в Logstash строку `trace_id|namespace|лог`, Logstash парсит ее общим пайплайном и отдает готовое событие обратно HTTP-запросом на `POST /api/event`, backend возвращает его в браузер.

## Быстрый старт

```bash
docker compose up -d --build
```

Открыть `http://localhost`.

Файл `.env` уже лежит в репозитории (в нем только пины версий и порты). Если его нет, возьмите шаблон: `cp .env.example .env`.

Требования:

- macOS на Apple Silicon (arm64) и Docker Desktop с плагином compose. Docker Desktop должен быть запущен: без него `docker compose` не отвечает, а без `docker.sock` не работают вкладка Logs, статус и рестарт.
- Около 4 ГБ свободной RAM: heap Logstash фиксирован `-Xms2g -Xmx2g`.
- Свободные порты 80, 1514, 9600. На macOS порт 80 свободен по умолчанию, но его может занять другой локальный веб-сервер.
- Файлы пайплайнов идут в контейнер через bind-mount Docker Desktop, поэтому hot-reload срабатывает с задержкой около секунды-двух после сохранения.

## Рабочий цикл

1. Вкладка **Pipeline**: загрузите свой `.conf` или создайте файл из шаблона. Парсер - это обычный `filter { }`, без `input` и `output`.
2. Вкладка **Debug**: вставьте лог и укажите Namespace.
3. Смотрите поля в dot-notation: фильтр по имени, сравнение событий, Diff с прошлым результатом, экспорт в CSV, JSON и mapping для ES. Если Logstash не вернул событие для части строк, они показываются отдельным списком под редактором.
4. Поправили парсер - сохранили. Если Logstash конфиг не принял, UI покажет ошибку перезагрузки.

Парсер `20-http-demo.conf` (создайте файл в Pipeline, это просто пример):

```ruby
filter {
  if [@metadata][namespace] == "demo" {
    grok {
      match => { "message" => "%{IPORHOST:client.ip} %{WORD:http.method} %{URIPATHPARAM:url.path} %{NUMBER:http.response.status_code:int}" }
    }
  }
}
```

Лог `10.1.2.3 GET /login 200` с Namespace `demo` даст:

```
client.ip                    10.1.2.3
http.method                  GET
http.response.status_code    200
url.path                     /login
```

## Namespace

Значение из поля Namespace попадает в `[@metadata][grokstash_ns]`, оттуда копируется в `[@metadata][namespace]`. Это единственный способ направить лог в нужный парсер:

```ruby
filter {
  if [@metadata][namespace] == "my_source" {
    # разбор
  }
}
```

Список для автоподстановки собирает backend из всех `.conf` (`GET /api/namespaces`) и отдает в UI. Список обновляется при открытии вкладки Debug и после загрузки нового файла; после правки namespace в существующем файле обновите страницу.

## Пайплайны

- Все `.conf` из `logstash/pipelines/` грузятся в один пайплайн `main`, порядок - алфавитный по имени файла. Переименование с числовым префиксом и есть сортировка.
- `01-input.conf` - единственное место с `input` и `output`: прием на `GROKSTASH_SYSLOG_PORT`, вывод в `stdout` (только нераспарсенное) и HTTP-запрос на `backend:4000/api/event`. Остальные файлы содержат только фильтры.
- Отключенные файлы лежат с расширением `.conf.disabled`, в выборку `*.conf` они не попадают.
- Файлы, которые нельзя менять из интерфейса, перечисляются в env `VENDOR_PIPELINES` (через запятую) и читаются в `backend/app/config.py`. По умолчанию список пуст. Такие файлы в UI помечены `vendor`, открываются только для чтения, а API отвечает 403 на их правку, удаление и переименование; чекбокс «Скрыть вендорские» убирает их из списка.
- `example.conf` - демонстрационный парсер syslog-connector, обычный редактируемый файл. К нему привязаны фикстуры из `fixtures/`.
- `patterns/` - grok-паттерны, доступны и Logstash, и конструктору в UI.

## Регрессия

Чтобы правка парсера не ломала уже разобранные логи, есть фикстуры: `fixtures/*.json`, по файлу на кейс.

```json
{
  "name": "example-syslog-login",
  "namespace": "syslog-connector",
  "log": "<134>1 2020-12-28T15:49:43Z myhost myapp 1234 ID47 [a x][b y] user login failed",
  "expect": {
    "host.name": "myhost",
    "process.name": "myapp",
    "siem.event.name": "ID47"
  }
}
```

- Вкладка **Regression** прогоняет все фикстуры через Logstash и показывает расхождения по полям: ожидалось, получено.
- В Debug есть кнопка «В фикстуру»: берет текущий лог, namespace и поля результата (кроме `@timestamp`, `trace_id`, `json_data_output`, `host.*`, `metadata.*`), и создает файл.
- В комплекте две фикстуры к `example.conf`, так что вкладка работает сразу после запуска.
- Поля сравниваются как строки, лишние поля в событии не считаются ошибкой. Отдельно проверяется, что событие не получило тег `_grokparsefailure`.

## API

Все ручки под `/api/`, реализация - FastAPI в `backend/app/` (роутеры в `backend/app/routers/`): пайплайны (список, чтение, запись, загрузка, переименование, включение, удаление), разбор лога `POST /api/log/trace`, perf-тест `POST /api/perf`, grok-паттерны `/api/patterns`, список namespace `/api/namespaces`, история разбора `/api/trace/history`, статус перезагрузки конфига `/api/logstash/reload`, логи и рестарт Logstash, фикстуры (`/api/fixtures`, `/api/fixtures/run`), прием событий от Logstash `POST /api/event`, `GET /api/health`.

## Тесты

```bash
docker run --rm -v "$PWD":/repo -w /repo/backend grokstash-backend:latest \
  sh -c 'pip install -q -r requirements-dev.txt && python -m pytest tests -q'
```

Фронтенд собирается с проверкой типов: `npm run build` = `tsc --noEmit && vite build`, в Docker это делает `docker compose build frontend`. Те же шаги в `.gitlab-ci.yml`. Фикстуры в CI не прогоняются: для них нужен запущенный Logstash.

## Возможности

- Debug: авторазбор с дебаунсом, ручной запуск, загрузка файла с логами, фильтр полей, сессия в localStorage.
- Сравнение событий и Diff после правки парсера, экспорт в CSV, JSON, mapping для ES.
- Редактор пайплайнов: сортировка drag&drop, включение и отключение, дублирование, шаблоны, поиск по всем `.conf`.
- Grok-конструктор: выделили фрагмент лога, назначили паттерн, получили grok и вариант через dissect.
- Регрессия: фикстуры с ожидаемыми полями, прогон одной кнопкой, отчет о расхождениях.
- Вкладка Logs: уровень, статус контейнера, память, рестарт.

## Ограничения

- **Аутентификации нет.** Любой, кто достучится до порта 80, может править и удалять пайплайны и перезапускать Logstash: backend работает с `docker.sock`. Поэтому UI и API Logstash опубликованы только на 127.0.0.1; syslog-вход 1514 слушает все интерфейсы, чтобы принимать логи с других хостов.
- Порт syslog задается в `.env` (`GROKSTASH_SYSLOG_PORT`) и подставляется в `01-input.conf`; после смены нужен `docker compose up -d`.
- Grok-конструктор проверяет паттерн упрощенно, заменой `%{NAME:field}` на регулярку. Это подсказка, а не проверка grok: окончательный результат смотрите в Debug.
- Perf-тест считает события, реально вернувшиеся на обратный канал, но не разделяет parse time и время доставки. Для оценки порядка величин годится, для бенчмарка - нет.
- Обратный канал HTTP, по одному запросу на событие: при недоступном backend Logstash делает одну повторную попытку и теряет событие. UI покажет такую строку как неразобранную в ответе `failed`.
- Сохранение `.conf` останавливает и заново поднимает пайплайн, поэтому 2-10 секунд после сохранения прием логов не работает. UI сам проверяет результат перезагрузки и показывает текст ошибки, если Logstash конфиг не принял.
- Один пайплайн `main`: нельзя запустить два набора фильтров параллельно или изолировать источники друг от друга.

## Решение проблем

**Docker Desktop не запущен** - `docker compose` не отвечает, вкладка Logs и рестарт возвращают ошибку: запустите Docker Desktop и дождитесь статуса Running.

**Logstash не стартует** - ошибка в одном из `.conf`: смотрите вкладку Logs или `docker compose logs logstash`. В UI после сохранения всплывает текст ошибки перезагрузки.

**Конфиг не принят, но лог разбирается по-старому** - Logstash оставил предыдущую версию пайплайна и пишет ERROR в лог на каждой попытке перезагрузки. Исправьте файл и сохраните еще раз; если не помогло - `docker compose restart logstash`.

**Правка не применилась** - перезапустите: `docker compose restart logstash`.

**Не хватает памяти или занят порт 80** - правьте `LS_JAVA_OPTS` и публикацию порта в `docker-compose.yml`.
